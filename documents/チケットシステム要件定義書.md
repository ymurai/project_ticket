# チケットシステム要件定義書

**プロジェクト名**: Theater Ticket Lite
**作成日**: 2025‑05‑18
**版数**: 0.5 （CI/CD セクション追加）

---

## 1. 目的

小規模〜中規模の演劇公演向けに、オンラインでチケット販売・発券・来場受付までを一元管理できる軽量 OSS を開発し、GitHub で公開する。固定座席管理・オンライン決済を排して MVP 実装コストを抑えつつ、**公演／ステージ／会場キャパシティ／券種**を登録管理し、**利用者ごとのロール権限**で安全に運用できる拡張性を確保する。

## 2. 背景・課題

* 既存 SaaS は機能過多・手数料高で個人劇団には負担となる。
* 公演規模は定員 50〜300 席が中心で自由席運用で十分。ただし **券種別価格** や **会場キャパシティ** と **役割別アクセス制御 (RBAC)** を満たさないと現場運用に乗らない。
* 個人制作のため、初期リリースでは決済機能を実装せず、後日 Stripe 連携を拡張機能として追加予定。

## 3. 用語定義

| 用語              | 定義                                                  |
| --------------- | --------------------------------------------------- |
| **Event**       | 公演 (例:『夏の夜の夢』)                                      |
| **Stage**       | ステージ。日時・会場を持つ                                        |
| **Venue**       | 会場。キャパシティを保持する                                      |
| **TicketType**  | 券種 (前売り／当日予約／学割など) と価格を定義                           |
| **Order**       | 観客の予約単位。券種・枚数を含む                                    |
| **Ticket**      | 1 枚の発券データ。QR トークンを保持                                |
| **SystemAdmin** | システム全体の設定・ユーザ管理を行う最上位権限                             |
| **Organizer**   | 公演主催者。Event/Stage/TicketType/Venue を CRUD できる |
| **Staff**       | 主催者が招待するスタッフ。Organizer と同等権限 (公演単位で制限可)             |
| **Checker**     | 受付担当。当日、売れたチケット一覧閲覧とチェックイン操作のみ可能                    |
| **Customer**    | 一般観客。チケット購入と自身の購入履歴閲覧ができる                           |

## 4. スコープ

### 4.1 取扱対象

* Event / Stage / Venue / TicketType の CRUD (Organizer/Staff 権限)
* ステージごとの在庫計算 (Venue.capacity - sold)
* Web フォームによるチケット予約 (Customer 権限、決済なし)

  * 予約時に **券種選択** 必須
* 予約確認メール送信 (QR 含む)
* QR／URL によるチェックイン (Checker 権限)
* 残席・販売数 CSV エクスポート (Organizer/Staff 権限、券種別集計)
* **RBAC**：JWT セッションでロールごとに API/画面をガード

### 4.2 非対象 (将来拡張)

* 固定席 (座席マップ) 予約
* オンライン決済、割引コード、ポイント
* 多言語 UI・複数通貨
* SSO / OAuth 外部ログイン

## 5. ステークホルダー & ロール

| ロール             | 主な操作                   | 主な関心事               |
| --------------- | ---------------------- | ------------------- |
| **SystemAdmin** | ユーザ招待・ロール付与・環境設定       | 障害対応、権限漏れ防止         |
| **Organizer**   | 公演/回/会場/券種 CRUD、売上 CSV | 公演運営の効率化            |
| **Staff**       | Organizer と同等 (委譲)     | 当日の運用負荷軽減           |
| **Checker**     | チケット一覧閲覧、QR チェックイン     | 受付速度、重複入場防止         |
| **Customer**    | チケット購入、履歴閲覧            | 購入 UI の簡潔さ、リマインドメール |
| **開発者コミュニティ**   | コード品質、ライセンス            | OSS コントリビュートしやすさ    |

## 6. 前提・制約条件

1. システムは OSS として MIT または Apache‑2.0 ライセンスで公開する。
2. 初期リリースは Fly.io 無料枠で稼働可能なリソースに収まること。
3. データベースは SQLite (開発) と PostgreSQL (本番) に対応する。
4. 個人情報はメールアドレスのみを必須とし、氏名は任意入力とする。
5. QR トークンは UUIDv4 を用い、推測困難性を確保する。
6. 認証は **email + magic‑link** を採用し、JWT にロールを付与 (実装容易性重視)。

## 7. 機能要件

### 7.1 認証・認可

* メールアドレス入力 → Magic Link でログイン (Customer〜Checker)
* SystemAdmin は `.env` に定義した初期アカウントでサインイン
* ロールごとに Next.js middleware で画面 / API をガード

### 7.2 管理機能 (Organizer/Staff)

* Event / Venue / Stage / TicketType の CRUD
* ホーム (統計カード・公演一覧・クイックアクション・最近の活動表示)
* 公演単位のホーム (残席 / 売上)→公演情報、と呼称
* CSV エクスポート (券種別枚数・金額)

### 7.3 受付機能 (Checker)

* 公演選択 → 当日受付画面 (リアルタイム残数表示)
* QR / 手入力検索で Ticket 検索 → チェックイン更新

### 7.4 観客機能 (Customer)

* ステージ一覧・券種選択 → 予約
* 予約完了メール (QR リンク)
* マイページで購入履歴・QR 再表示

## 8. 非機能要件

| 項目         | 要件                                         |
| ---------- | ------------------------------------------ |
| **性能**     | 100 同時アクセスでレスポンス < 2 秒 (95%tile)           |
| **可用性**    | SLA 99% (OSS 参考値)                          |
| **セキュリティ** | TLS, CSRF/XSS 対策, RBAC, QR 署名検証            |
| **可観測性**   | ログ (JSON)、Fly Metrics                      |
| **保守性**    | ESLint / Prettier / Vitest / Playwright CI |
| **拡張性**    | Prisma ORM / modular services              |

## 10. ユーザーストーリー (抜粋)

* **US‑01** SystemAdmin はスタッフを招待しロールを付与できる …
* **US‑02** Organizer は公演とステージを登録し残席を確認できる …
* **US‑03** Customer は券種を選んでチケットを予約し履歴を閲覧できる …
* **US‑04** Checker は QR を読み取り入場させられる …
* **US‑05** Staff は Organizer と同等にホームを操作できる …

## 11. 外部インターフェース

* **メール API**: Resend REST v1 (`POST /emails`) — Magic‑link と予約メール送信
* **QR**: `https://<domain>/checkin/{token}` 形式の URL
* **Webhook (将来)**: Stripe `payment_intent.succeeded` → `POST /api/webhooks/stripe`
* **CLI (将来)**: `npm run export -- --event=<id>` で CSV 出力

## 12. CI/CD

### 12.1 GitHub Actions ワークフロー

| ジョブ名                 | トリガー                                  | 主な処理                                                                             |
| -------------------- | ------------------------------------- | -------------------------------------------------------------------------------- |
| **build‑test**       | `push` / `pull_request`               | `pnpm install` → Lint → Vitest (unit) → Playwright (E2E) → `prisma migrate diff` |
| **docker‑image**     | `push` on `main` & Tag (`v*`)         | Build multi‑arch Docker image → Push to GHCR                                     |
| **deploy‑fly**       | `workflow_run` (docker‑image success) | `flyctl deploy --image ghcr.io/<repo>:<sha>`                                     |
| **nightly‑snapshot** | `schedule` (cron: 03:00 JST)          | `fly pg snapshot create` & retention cleanup                                     |

### 12.2 Quality Gates

* テスト成功率 100%（Vitest + Playwright）
* ESLint / Prettier Warnings 0
* CodeQL 脆弱性 0

### 12.3 シークレット管理

`RESEND_API_KEY`, `FLY_API_TOKEN`, `DATABASE_URL` を GitHub Secrets に保存し、各ワークフローで `env:` に注入。

## 13. 運用・保守

* **デプロイ**: GitHub Actions → Fly.io `production` app
* **バックアップ**: Fly Postgres Nightly Snapshots (保持 7 日) + 手動 `fly pg snapshot restore`
* **監視**: Fly Metrics + 外形監視 (Uptime Kuma 推奨)
* **障害対応**: `README` に rollback / restore 手順を記載

## 14. ライセンス

MIT ライセンスを採用予定。コントリビューターは DCO 署名 (Developer Certificate of Origin) を必須とする。

## 16. リスク & 対策

1. **CI ブレイク**: Branch Protection で `build‑test` 必須ステータスを設定。
2. **権限漏洩**: RBAC ミドルウェアに対する統合テストを継続的に実行。
3. **大量予約 BOT**: rate‑limit middleware + CAPTCHA v3 を導入。
4. **メール不達**: Resend のバウンスログを毎晩チェックし、リトライキューを実装 (将来)。
